Part 1

Governance

How the system is structured, maintained and versioned.

G1

About this system

EDU 360 has one design system with two layers. Foundations and components (Parts 2–3) own every visual value and shared behaviour. Product patterns (Part 4) apply them to EDU 360 workflows and must not redefine them.

Layer 1

Foundations & components

The only source of tokens (colour, type, spacing, radius, sizing, elevation, motion), icons, accessibility rules and the canonical component library.

Go to foundations

Layer 2

Product patterns

EDU 360 screens, roles, workflows, education modules, security and governance. Patterns compose Layer 1 components; they never introduce new tokens.

Go to product patterns

Authority rules

  1. If a value is needed that does not exist, propose it as a change to F9 · Token reference. Never add a local hex value, radius or spacing in a screen.
  2. Product business behaviour comes from the V3.3 source documents (master document, Permission Matrix, Action List, Database Design, API Contract). This system presents that behaviour; it does not decide it.
  3. Where the source does not settle a behaviour, the system marks it Decision required and lists it in P12.
  4. Interface visibility is never authorisation. The server checks every action, scope and workflow state. This rule is stated once here and applies to every pattern in this document.

Maintenance, contribution and versioning

Ownership

One design-system owner approves token and component changes, with an engineering counterpart for the code library. Decision required Names to be assigned.

Contribution

Raise a proposal with the problem, affected screens, proposed spec and accessibility check. Changes ship to Figma and code in the same release.

Versioning

Semantic versioning. Major: removed or renamed token or component. Minor: new token, component or variant. Patch: documentation or bug fix. Deprecations stay for one minor release with a migration note.

Part 2

Foundations

Canonical visual and interaction values. Every component and product pattern consumes these and nothing else.

F1

Principles

Calm and trustworthy

Neutral surfaces carry most of the interface. Brand and status colours appear only where they carry meaning.

Task first

Each screen leads with the user's next action in their active role and scope, not with decoration or vanity metrics.

Explain state

Say what happened, what is saved, what is pending and what the user can do next. Never leave a silent failure.

Context always visible

Institution, academic year, active role and record status stay visible wherever they change the meaning of what is shown.

Accessible by default

Keyboard, screen reader, zoom and touch work from the first build. Colour never carries meaning alone.

Consequences before commitment

Sensitive, financial and irreversible actions show the object, effect and reversibility before the user confirms.

Rules

  • Weights in use: 400, 500, 600, 700, 800 (DM Sans) and 700, 800 (Manrope). Headings use Manrope 700; 800 is reserved for the brand name.

F6

Iconography

Outline icons on a 24 × 24 grid with a 2 px stroke, round caps and joins, coloured with currentColor. Delivered as an SVG sprite; production may substitute a matching open-source set (for example Lucide) if names map one-to-one.

home calendar check-circle alert error info x-circle search bell user users chart book wallet upload download lock shield clock eye edit send return archive ban refresh printer wifi-off more help
  • Sizes: 16 px inline with caption text, 20 px default, 24 px navigation and empty states.
  • Decorative icons next to a visible label get aria-hidden="true".
  • Icon-only buttons are allowed only for universally understood actions (close, menu, more, previous, next, search, notifications). They need an aria-label and a tooltip on hover and focus.
  • Status icons are fixed: success = check-circle, warning = alert, danger = x-circle or error, info = info, draft = edit, returned = return, archived = archive, denied = ban.
  • Do not use emoji or Unicode symbols as icons (for example ♧ for notifications); they render differently on each platform and are read aloud unpredictably.

Imagery and illustration Proposed

Illustrations use flat shapes in brand-soft, warm surface and accent, with no text inside the image. They are decorative (aria-hidden) and removed at sm when space is tight. Profile photos appear only when the user has provided one; initials are the fallback. Logo lockup and clear space: Decision required.

F9

Token reference and design-to-code contract

The CSS custom properties at the top of this file are the source of truth. Export them to JSON (W3C Design Tokens format) with Style Dictionary and sync the same names to Figma variables.

Naming convention

  • Primitive: --p-{hue}-{step}, for example --p-green-600. Never referenced by components.
  • Semantic: --{category}-{role}-{variant}, for example --color-text-muted, --color-status-warning-bg, --space-4, --radius-md.
  • Component: --{component}-{property}, added only when a component genuinely needs its own value, for example --button-height.
  • All lowercase kebab-case. No camelCase. No product prefix: the whole system is EDU 360.

Component engineering contract

  • Components expose semantic variants (variant="primary|secondary|tertiary|danger") and explicit disabled, loading and invalid states.
  • Components never hard-code role names, permissions or business rules; they receive allowed actions as data.
  • Formatting, validation and authorisation are separate concerns.
  • Components never fetch data or mutate records just by rendering.
  • Every component has a stable test ID and Figma Code Connect mapping. Not implemented

        P8

        Financial integrity

        Requirements

        • Currency, exact amount, line items, adjustments and total shown separately, in ₹ with two decimals.
        • Review step before posting; the confirm button states the amount: "Post ₹53,400.00".
        • Draft structures and posted records look different (badge and read-only state).
        • Posted receipts are immutable and carry a stable reference.
        • Reconciliation shows unmatched items and their resolution state.
        • Failed or incomplete payments say whether money moved.

        Confirmation content

        • Object and scope affected
        • Amount and currency
        • Whether it can be reversed, and how
        • Reason, where policy requires one
        • Warnings for duplicates, mismatches or locked periods
        • Server-confirmed final status and reference
        Decision required

        Credit consumption, the reconciliation-resolution action (OD-133), receipt numbering after restore and auto-relock behaviour are unresolved. Do not design UI that assumes them.

        P10

        Performance and resilience

        Many students and parents use low-cost Android phones on mobile data. Design and build for that first.

        Budgets Proposed

        • First meaningful content under 3 s on a mid-range Android over 4G.
        • Fonts: 2 Latin families, 6 weights total, font-display: swap; Indic subsets on demand.
        • Images: responsive sizes, WebP/AVIF, lazy-loaded below the fold; no photo backgrounds.
        • Charts load after primary content; a failed chart never blocks the task.

        Resilient interaction

        • Skeletons for regions; never block the whole page for one panel.
        • Prevent double submission; use server idempotency keys for payments, approvals and attendance.
        • Optimistic updates only where rollback is clear; never for money or approvals.
        • Long jobs (imports, exports, reports) show status, start time, progress, result and retry.
        • Version conflicts show a compare-and-reload path; never overwrite silently.

        P11

        Print and export

        • Receipts, report cards, certificates, timetables and registers have print layouts. This page includes a print stylesheet: navigation, toasts and controls are hidden, colours switch to black on white, tables avoid page breaks.
        • Printed records show institution name, reference, generated date and time with time zone, and page numbers.
        • Status badges print with a black outline and text, so meaning survives greyscale printing.
        • PDF exports are generated server-side from the same template, permission-checked and audited.
        • CSV exports use ISO dates and plain numbers (no ₹ or grouping) and list the applied filters in the file name or header.
