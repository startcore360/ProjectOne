# EDU 360 V4.0 Spec Package — Summary & Navigation Guide

This file digests `docs/EDU360_V4.0_Final/` (10 deliverables: product spec, governance register,
roles/permissions, database architecture, API spec, QA traceability, UX/workflow, security
compliance, design system, interactive prototype). Every file in that package — including the
large ones (the 1.4MB OpenAPI yaml, the 2.1MB UX workflow HTML, the full SQL migration bundle, and
every xlsx sheet including historical change logs) — has been read in full, not sampled, to
produce this summary. Figures below are quoted exactly as found in the source, with discrepancies
between sources flagged rather than silently resolved.

That package is a **target-state SaaS design**, written and validated almost entirely on paper
(plus one throwaway Postgres cluster) — it does **not** describe the current repository. Read this
file before opening any of the raw deliverables; it tells you what's actually in them and exactly
which one to open for a given question (§8).

**One-paragraph reality check:** the actual codebase (`api/`, `app/`) is a single-tenant Spring
Boot monolith with 6 backend feature packages, 18 REST endpoints, 2 roles (`TEACHER`, `STUDENT`),
H2-in-dev/unconfigured-Postgres-in-prod, and a 2-page React frontend (login + one dashboard). The
V4.0 package specifies a multi-tenant SaaS with 71 roles, a 278-action permission matrix, a
206-table RLS-enforced Postgres schema (97/97 tests passing against a real throwaway Postgres
cluster), a 408-operation/313-path OpenAPI contract, 29–30 functional modules, 60 approval chains,
and a full design system/prototype — roughly two orders of magnitude larger in scope than what
exists in code today. Treat every fact below as "what V4.0 wants," never as "what the app does."

## 1. Product scope — `01_Master_Product_Specification/EDU360_V4.0_01_Master_Product_Specification.md`

**What EDU 360 is:** a multi-tenant SaaS for education management, India-first (INR billing,
India-only launch, English-only v1, one responsive installable web app, no native mobile apps in
v1). The **tenant** is the billed customer: either a university group (with its colleges/schools
under it) or a single standalone college/school. Hierarchy: **Platform → Tenant → University
(group tenants only) → Institution (College/School) → Department → academic structures → users.**
A user can hold multiple role assignments, but only one is active per request.

**Phase 1 (v1) modules** (20 of the 29/30 catalogued modules — see §6 for the exact-count
discrepancy in the source itself): sign-in/account, users & roles, institution setup/academic
structure, timetable & online classes, attendance, examinations, results, assignments/homework/
study material, fees, leave, communication, community feed & events, complaints, student notes,
policies/documents, staff records, risk monitoring, reports/dashboards, data import/search,
governance & data protection, platform administration.

**Phase 2 (4 modules):** payroll (payslips only — EDU 360 never disburses salaries), library,
placement, admissions (WhatsApp channel).

**Phase 3 (5 modules):** hostel, transport, alumni, research/publications, API & integration
governance.

**Explicitly out of Phase 1** (don't build yet): refunds, partial fee payments, tax handling,
re-evaluation, moderation queues, WhatsApp, report-abuse, custom report builder, alumni login —
enforced at the DB level (triggers reject partial allocations and there is no `REFUND` ledger
type in the committed schema).

**Explicitly out of scope entirely:** physical biometric hardware, physical ID-card printing (data
only exports to a vendor), campus surveillance, native mobile apps, GPS vehicle tracking, and
actually disbursing payroll.

**Decided tech stack (target, not current):** React (per-tenant) + API Gateway + Keycloak
(OIDC/OAuth2 + MFA) fronting **independent per-domain Spring Boot services from day one** (not a
monolith) + PostgreSQL (DB-per-tenant by default, shared+RLS for small plans) + Redis +
RabbitMQ-or-SQS (still an open decision, see §5) + S3 + OpenSearch. Deployment: AWS India regions
(Mumbai/Hyderabad), CloudFront → API Gateway → ALB → EKS → RDS Postgres, with a stated
Azure-portable equivalent. Razorpay is the decided default payment gateway. JWT claims carry
`role, tenant_id, scope, permissions`. 206-table data model, OpenAPI 3.1.0 with 408 operations
(§4).

**Key business rules worth knowing cold:**
- **Attendance statuses** are a fixed enum: `PRESENT`, `ABSENT`, `ON_APPROVED_LEAVE`, `NOT_HELD` —
  there is explicitly no "Late" status.
- **Results** flow `Draft → Submit → HOD/Class-Teacher review → Principal approval → publish`,
  and the publisher is mode-specific — enforced in SQL by `fn_publish_gate()` (§3): school →
  `SCHOOL_PRINCIPAL`/`SCHOOL_ADMIN`; college-under-university → `CONTROLLER`; standalone/external
  college → `COLLEGE_ADMIN`. A mismatch is a hard-rejected DB state (`WRONG_PUBLISHER_FOR_MODE`).
- **Fees:** structures follow `DRAFT → PENDING_APPROVAL → LIVE → SUPERSEDED/REJECTED` and freeze
  once they leave `DRAFT`; line-sum must equal installment-sum; exactly one open online payment
  per account; **no partial payments** — `fn_allocation_guard()` requires the paid amount to equal
  net due exactly; append-only ledger with financial year auto-derived as April–March; no refunds
  in v1.
- **136 open decisions** remain in the governance register (see §2) — several explicitly block
  engineering start on the areas they touch (DB major version, institution-level RLS scope,
  attendance granularity, Keycloak realm model, field encryption, search isolation, migration
  tooling, RabbitMQ-vs-SQS/SES-vs-SendGrid, offline attendance sync design, pilot/UAT governance).

- **University (13):** Vice Chancellor, Registrar, Finance Director, Controller of Examinations,

- **College (33):** Principal, Vice Principal, College Admin, College Accountant, College Audit

  Office Staff, Admission Officer, Examination Clerk, Records Officer, Librarian, Library

- **School (15):** School Principal, Vice Principal (School), School Admin, School Accountant,

- **External (1):** Applicant.

Total 6+3+13+33+15+1 = 71. Many college/school/support roles are explicitly Phase 2/3, not live in
Phase 1.

**Permission model:** access is driven by a **278-item action list** (234 Phase 1 / 32 Phase 2 /
12 Phase 3, per `06_ref_checks.sql`'s asserted counts). Each role gets a letter per functional area
(28 feature areas) in a master matrix — **1,988 matrix cells, 1,851 role×action pairs** (exact,
from `06_ref_checks.sql` and the governance V4.0 Correction Log):
`F` = Full, `M` = Manage, `C` = Configure, `A` = Approve (only at the one chain step the role
holds), `V` = View, `R` = Request, `N` = No access — combinable (e.g. `M+A`). Rules: every
non-`N` letter must be backed by a concrete action; where a letter and a role's free-text
"Restrictions" conflict, the restriction wins. **`F` and `M` never imply approval power** —
approval only comes from a formal approval chain (60 chains, §6), and nobody ever approves their
own request. **101 of the 278 actions are flagged sensitive** (per `06_ref_checks.sql`).

The **"Scoped Letters" and "Cell Notes" sheets in the roles workbook are current-state primary
sources, not history** (an earlier pass mistakenly grouped them with the change logs) — they hold
the actual scope text behind every non-trivial letter, e.g.:
- Management's Finance `A` in a standalone institution = "sets fee policy and approves fee
  exceptions."
- Governing Body Approver's Leave `A` = "only the Principal's/VC's/a dedicated DPC's own leave,
  where this role is the set approver."
- Class Teacher holds `M` (not `F`) on Exams specifically so teachers "enter marks but never
  approve results."
- IT Administrator is scoped to accounts/security/backup only — no academic/finance data.
- Billing Manager / Support Manager (platform staff) are explicitly barred from tenant
  Finance/Communication data.
- "Sandwich rule" is a named leave-config concept Admin configures but never approves.

On top of the base matrix:
- **Custom roles / templates:** tenants derive custom roles from baseline templates via governed
  "Template Action Map"/"Template Governance" sheets, not ad hoc permissions. Per the UX HTML's
  `GUARD_CUSTOM_ROLE` rule: custom roles can never override a role's "Never allowed" restrictions,
  and sensitive-data rights are explicit, never inherited by default.
- **Delegation & Separation-of-Duties (SoD)** — hard rules confirmed across multiple sources
  (governance register + UX `GUARD_*` nodes + SQL `fn_delegation_guard`): nobody approves their
  own request; one actor can't decide two steps of the same request chain; rejection requires a
  remark and ends the request (no send-back, no auto-advance — only reminders); delegation is
  date-bounded, only to a same-or-higher role or a designated deputy (Principal→Vice-Principal is
  the one closed exception); a delegate can't re-delegate, and can't act on a request they raised,
  are the subject of, or already acted on; merit-list/DPO approvals are never delegated or
  bulk-approved; preparer ≠ approver for compliance/accreditation items.
- **Role lifecycle & audit:** roles have a tracked lifecycle (creation, assignment, deactivation)
  with audit logging — not a static enum. Every create/edit/delete/approval/export/login/
  denied-attempt/sensitive-data-view is logged (`GUARD_AUDIT`).
- **Platform/tenant isolation:** platform roles cannot access tenant data at all, except a
  defined, tenant-granted, ticket-bound, **read-only, 24-hour-capped** Support exception
  (`GUARD_PLATFORM_ISOLATION`) — matches the SQL's `support_access_grant`/`support_tickets`
  tables and the all-schemas-isolated `edu_platform` vs. `edu_app` role split (§3).
- **Role roll-down (V4-PD-01, new in V4.0):** if a role/level has no active holder (e.g. a
  standalone school with no Registrar), its authority automatically falls to a defined stand-in,
  tracked via "Acting for …" audit badges (`acting_for_role` column, §3). Full ruleset
  `V4-RD-01`…`V4-RD-09` (from the QA workbook's "Roll-down Requirements" sheet, backed by SQL
  `DB-80`–`DB-97` tests): preference-ordered stand-ins; resolves to `HOLDER` / `ROLLDOWN` /
  `WITHHELD` / `UNRESOLVED` (loop or no holder); only **non-approval** rights can be withheld by a
  tenant override — an unapprovable approval would block forever, so approvals can never be
  withheld; a stand-in must be a real, non-personal role; a **never-roll-down list** is enforced
  by DB CHECK + trigger (platform roles, Student, Parent, Applicant, Governing Body Approver, and
  teaching roles); and — a specific, non-obvious rule — **the Governing Body Approver loses its
  roll-down authority entirely once a tenant has an actual Management role assigned** (decision
  V4-PD-01, Product Owner, 2026-10-30).

**Biggest open gaps** (from "Open Decisions 136" / "Audit Findings 54" / GAP sheets — most
consequential, not exhaustive): Postgres major-version pinning; whether institution-level RLS also
enforces `institution_id` isolation (proposed, not closed — though it's actually implemented as a
`RESTRICTIVE` policy per §3, so this one may be more resolved in SQL than the decision register
admits); attendance granularity model; data retention durations per data class (needs legal
sign-off — explicitly **not yet reviewed by counsel** per one fork's finding); offline attendance
sync/conflict handling; per-setting configuration precedence; audit-store interface/integrity
method; Keycloak identity-linkage model; shared→isolated tenant migration procedure; student-ID
uniqueness scope; role-ranking used for delegation eligibility; duplicate-record matching rules;
one High-severity security finding was open because its own source document ("Role and Permission
Management Rules") was never supplied — as of 2026-11-04 the Product Owner approved that
document's content for the next requirements revision (see `../GOVERNANCE_DECISION_LOG.md`,
decision SOURCE-GAP, and `../ROLE_PERMISSION_MANAGEMENT_RULES_ADDENDUM.md` for exactly what was
approved); this closes the documentation gap going forward but is not a retroactive change to
V3.3 and is not yet reflected in any code. All other items remain tagged "Open," not resolved —
several are marked blocking ("B").

**Version-history sheets — verified, not just assumed, to be superseded:** the "Change Log
V1→V3.3" sheets are *not* pure noise — they document *why* specific letters/roles ended up as they
did (e.g. `CERTIFICATE_APPROVE`/`GOVERNANCE_ITEM_APPROVE` moved from Accreditation Coordinator to
Compliance Officer/Principal between V3.2→V3.3; `GRADUATION_CONFIRM` scoped only to Controller of
Examinations/Records Officer). V3.3's own change log documents **114 letter-gap decisions**
reconciling the action count from 275→278 via 3 new actions (`PLATFORM_REPORTS_VIEW`,
`TENANT_OVERSIGHT_VIEW`, `INTEGRATION_SETTINGS_VIEW`). The governance register's "Source
Conflicts" sheet resolves 14 real contradictions between prior source documents (X-1…X-14), e.g.
whether a published "LIVE" academic structure can change before a session starts (resolved:
frozen after `DRAFT`) and a missing `payment_route`/`gateway_order` table one source assumed
existed (resolved by adding it). The "History V3.2 \*" sheets (31–34), by contrast, really are
fully superseded — every delta from them is already captured in the V3.3 change log; they add
nothing new.

**A genuine unresolved discrepancy worth flagging explicitly:** the governance register's "V4.0
Correction Log" sheet states the SQL test suite reports **79/79 tests PASS** (run 2026-10-30), and
gives headline figures of **71 roles, 278 actions (8 added), 1,851 role×action pairs, 570 workflow
steps, 60 approval chains, 690 declared FKs (711 incl. partition clones)**. The database bundle's
own `run_results.txt`, read in full, instead reports **97 tests (DB-01 through DB-97), 0
failures**, and a catalogue count of **696 declared FKs (717 incl. partition clones)**. These two
authoritative-looking sources disagree on the test count (79 vs. 97) and the FK count (690/711 vs.
696/717) for a run claimed to be the same date. The most likely explanation is that the governance
log's 79 counts only the V3.3-baseline + V4.0-specific tests it was tracking at the time it was
written, while `run_results.txt` reflects a later, more complete run (DB-01 through DB-97 spans
more than just the V4.0 additions) — but nothing in the committed files proves that. **Treat
`run_results.txt` as the more authoritative number** (it's the actual tool output, not a
hand-maintained log), but don't cite "97/97" as if the discrepancy didn't exist.

**Gap vs. current code:** `api/.../user/Role.java` is a 2-value enum (`TEACHER`, `STUDENT`) with
method-level `@PreAuthorize("hasRole(...)")` — no tenant/institution/college/school scoping, no
custom roles, no delegation, no SoD enforcement, no roll-down, no role lifecycle/audit trail. None
of the above mechanisms exist in `api/` today.

## 3. Database & technical architecture —
`04_Database_and_Technical_Architecture/EDU360_V4.0_04_...md` + `04_.../sql/*` (every file read in
full, including the large reference-data and test files)

**Target schema — exact counts from a full read of `01_schema.sql`:** **209 `CREATE TABLE`
statements** — **162 in `app`, 29 in `platform`, 18 in `ref`**. Of those, 3 are list-partitions
(`app.attendance_entry_y2025/y2026/y2027`, partitioned by `academic_year`), so there are **206
logical tables** with 3 being partitions of one parent.

> **Open discrepancy, not resolved by the committed files — flag, don't paper over:**
> `run_results.txt`'s own Postgres-catalog query (`pg_class`) reports **208 parent tables and 39
> partitions** after running the exact same migration chain — not the 206 parents / 3 partitions
> visible by reading the `.sql` files directly. A case-insensitive grep for `partition` across
> every non-test `.sql` file in the bundle finds nothing beyond the 3 attendance partitions. Where
> the other 36 partitions and 2 extra parent tables in the executed database came from is
> unexplained by anything in the repo. Do not assert either number as definitively correct without
> re-running `run_all.sh` yourself and inspecting the live catalog.

**Multi-tenancy:** every `app` table carries `tenant_id`. From a full read of `03_bindings.sql`:
exactly **159 `app` tables get `ENABLE` + `FORCE ROW LEVEL SECURITY`** with a mandatory
`p_tenant` policy (`tenant_id = current_setting('app.tenant_id', ...)`, fail-closed via `NULLIF`
guarding), plus an additional **`RESTRICTIVE p_institution`** policy on any table that also has an
`institution_id` column — so the second-layer institution scoping is already implemented in SQL,
not merely "proposed." **`platform` schema tables get no RLS at all** — their isolation is
physical (one DB per tenant), not row-level. Total across the bundle: **280 `CREATE POLICY`
statements, 208 `CREATE TRIGGER` statements, 369 `GRANT` statements, 0 `REVOKE` statements.**
(`run_results.txt`'s live catalog count differs slightly — 282 RLS policies, 217 triggers, and
**160** app tables with RLS forced, i.e. off by one from the 159 counted directly in the file —
consistent with the same unexplained gap noted above between committed-file counts and the
executed database.)

**Role model** (from `03_bindings.sql`, fully read): `edu_app` (read/write on `app` tables, the
normal application role), `edu_report` (read-only everywhere, for reporting), `edu_retention`
(the **only** role allowed to physically delete anything — `DELETE` on `student_note` past its
`delete_after` date, blocked if an active legal hold exists, plus `SELECT` on `legal_hold`),
`edu_shipper` (UPDATE only on 6 shipment-tracking columns of `audit_outbox`, for the
outbox-shipper background process), `edu_platform` (full access to the `platform` schema only).
`ref` tables are `SELECT`-granted to `edu_app`, `edu_report`, and `edu_platform`. Confirmed by a
dedicated test (`07_tests_extra.sql`, DB-55–DB-59): a **fresh** Postgres connection that never set
the tenant session variable gets zero rows back (fail-closed, not just on reset), and `edu_app`
gets `permission denied for schema platform` outright.

**Conventions:** UUIDv7 primary keys, `timestamptz` in UTC, `numeric(14,2)` for money,
**soft-delete only** (status/archive columns, never hard delete — reinforced by the fact that only
one narrowly-scoped role can ever issue a real `DELETE`), optimistic concurrency via a
`row_version` column touched by a generic `fn_touch` trigger, and an outbox pattern
(`audit_outbox`/`outbox_event` written in the same transaction as the business change, shipped out
by the `edu_shipper` role).

**What "rules" vs. "bindings" mean — now enumerated exactly** (full read of both files):
- **`02_rules.sql` (443 lines) — the logic.** **25 functions**, including generic helpers
  (`fn_touch`, `fn_append_only`, `fn_audit_guard` ×3 schemas) and domain-specific guards:
  `fn_note_guard` (student notes: no UPDATE ever, DELETE only by `edu_retention` past
  `delete_after`, blocked by a legal hold), `fn_gateway_event_guard`,
  `fn_institution_activation_gate` + `go_live_blockers()` (go-live requires a Principal/VC
  leave-approver to be set — matches `GUARD_MANAGEMENT_GO_LIVE` from the UX spec),
  `fn_leave_approver_not_subject`, `fn_approval_step_guard` (decided steps are immutable,
  self-approval blocked), `fn_delegation_guard`, `fn_guardian_limit` (max 3 non-blocked guardians
  per student), `is_term_locked`/`fn_attendance_entry_guard`/`fn_marks_entry_guard` (term-lock +
  partition-year + `NOT_HELD` mirroring), `fn_result_guard` (published results can only move to
  `WITHDRAWN`), **`fn_publish_gate`** (the exact `WRONG_PUBLISHER_FOR_MODE` mode/publisher
  matching logic from §1), `fn_fee_structure_child_lock`/`fn_fee_structure_guard` (the
  `DRAFT→PENDING_APPROVAL→LIVE→SUPERSEDED/REJECTED` state machine plus line-sum = installment-sum
  check), `fn_fee_line_range`, `is_period_locked`/`fn_ledger_guard` (April–March financial year,
  reversals must match account+amount+opposite direction), **`fn_allocation_guard`** (the
  no-partial-payment rule — paid amount must equal net due exactly), `fn_receipt_guard`
  (`ISSUED→VOID` only), `next_receipt_number` (gap-free sequence, tested to survive a simulated
  rollback), `fn_complaint_guard` (`RESOLVED` is final), `fn_attendance_correction_lock`,
  `fn_grade_band_lock`. Also **4 GiST exclusion constraints** preventing overlap — no two active
  staff assignments, no two overlapping full-day leave requests, no two overlapping active fee
  assignments, no two overlapping weekly-off rules for the same scope — and **4 views**
  (`v_installment_net_due`, `v_student_fee_balance`, `v_student_overdue_flag`,
  `v_student_dues_flag` — this last one has an explicitly open definitional question, OD-51:
  "dues" vs. "overdue"), all `security_invoker = true` so they respect the querying role's RLS,
  plus **18 named indexes** (trigram name search, partial indexes on attendance/leave/approval).
- **`03_bindings.sql` (1,017 lines) — the enforcement.** Actually attaches that logic: the 208
  triggers, 159 RLS-forced tables with their 280 policies, and the 369 grants described above.
  Split exists so logic and enforcement get reviewed separately.
- **`03b_fk_indexes.sql` (127 lines)** — **~96 `fkx_*` indexes**, each shaped
  `(tenant_id, institution_id, <fk_column>)`, confirming the composite-tenant-key indexing
  strategy is systematic, not incidental.

**V4.0-specific additions — exact mechanism, not paraphrase:**
- **`08_v40_rules.sql`** hardens `app.leave_approver_setting` so (a) the subject of a leave
  (Principal/VC/Data Protection Contact) can never be named their own approver, and (b) a
  `REGISTRAR`/`VICE_CHANCELLOR` approver-kind now requires the target user to actually hold an
  active assignment of that role (closing a loophole where a non-Registrar could be configured as
  the Registrar-kind approver). It also adds **8 missing FK indexes — all in the `ref` schema**
  (not `app`/`platform`), on `feature_catalog`, `module_dependency`, `standard_role_action`,
  `permission_matrix_cell`, `approval_chain_step`, `report_catalog` (×2), `setting_definition`.
  Rollback-tested in `08r_v40_rules_rollback.sql`.
- **`10_v40_rolldown.sql` (177 lines)** implements role roll-down: two new tables —
  `ref.role_rolldown_default` (global default stand-in table, 182 seeded rows per
  `10d_v40_rolldown_ref.sql`, covering 52 distinct roles that can roll down — matches
  `run_results.txt`'s `REFCHECK | roles with a roll-down | 52 | 52`) and
  `app.role_rolldown_override` (tenant-level override — `ASSIGN` a different stand-in, or
  `WITHHOLD`, restricted to non-approval actions). A new `acting_for_role` column on
  `approval_step` records roll-down-driven decisions. The resolver `fn_rolldown_resolve()` walks
  up to 6 hops through override→default, detects loops, and returns
  `HOLDER`/`ROLLDOWN`/`WITHHELD`/`UNRESOLVED`. A guard trigger `fn_rolldown_override_guard`
  enforces 8 rules (RD-G1..G8): fixed roles never roll down; approvals are never withheld; a
  stand-in must be a real, non-personal role; action-kind must match (approve vs. other); the
  setter must actually hold the role they claim to act as; and the Governing Body Approver's
  roll-down authority is revoked once a Management role exists for the tenant (§2).
  `10d_v40_rolldown_ref.sql` also seeds 2 new actions (`ROLLDOWN_VIEW`, `ROLLDOWN_OVERRIDE_SET`)
  and 9 new role-action pairs. `10r_v40_rolldown_rollback.sql` (9 lines) drops it all cleanly but
  **destroys any tenant overrides** — its own comment warns to export them first.

**`run_all.sh` (51 lines) — exact pipeline:** builds `edu360_v4_test` (runs

1. **Test-count disagreement:** governance register's "V4.0 Correction Log" says **79/79** tests
   pass; `04_Database_and_Technical_Architecture/sql/run_results.txt` (the actual tool output)
   says **97/97** (DB-01–DB-97). Trust `run_results.txt` as the primary source since it's generated
   output, not a hand-maintained log, but mention both if precision matters.
2. **Table/partition-count disagreement:** the committed `.sql` files show 206 logical tables (209
   `CREATE TABLE` statements, 3 of them partitions). The executed database's own catalog query in
   `run_results.txt` reports 208 parent tables + 39 partitions. Nothing in the repo explains the
   extra 2 parents / 36 partitions. Don't assert a single number without re-running `run_all.sh`
   and inspecting the live catalog.
3. **FK-count disagreement:** governance log says 690 (711 incl. partition clones); `run_results.txt`
   says 696 (717 incl. partition clones). Same root cause as #1/#2 — likely a snapshot-timing
   difference between documents, not independently verified.
4. **RLS-table-count off-by-one:** `03_bindings.sql` as committed forces RLS on 159 `app` tables;
   `run_results.txt`'s live catalog says 160.
5. **Module-count inconsistency *within a single file*:** the UX workflow HTML's own `MOD_HUB`
   label says "29 modules" while its own data array (`meta.modules`) has 30 entries.
6. **Action-code coverage gap:** 278 actions are catalogued (governance/roles workbooks), but only
   236 are actually wired to an OpenAPI operation — 42 catalogued actions have no corresponding API
   operation in the current contract.

None of these are resolved by anything in the repo today. Flag them if asked "exactly how many X
does V4.0 have" rather than picking whichever number sounds more precise.
