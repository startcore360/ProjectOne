4. Roles, assignments, active scope and permissions

The frontend role catalogue contains 71 source-defined dashboard personas. The catalogue is not itself an assignment list or an authorization grant.

Platform roles (6)

Product Owner, Platform Admin, Billing Manager, Support Manager, Release Manager, Data Protection Officer.

Platform console entry checks for one of these six platform role codes. The server loads /platform/me/permissions; navigation filters by action codes.

Tenant / institutional levels (65)

3 tenant-wide roles, 13 university roles, 33 college roles, 15 school roles and 1 external Applicant role.

A tenant user can hold multiple assignments, but one active assignment is used in a request. Scope is tenant, institution or department.

Active-role switch: GET /me returns the user's role assignments and current assignment. POST /me/active-role selects one assignment. The frontend then reloads /me/permissions. The code does not union permissions from multiple assignments.
71 roles
Role preview warning: /role-previews and /role-preview/:roleCode are development-only visual previews. The page says explicitly that the role is not activated, the signed-in user is not switched, and preview metrics / work queues are placeholders. Role templates are not effective role assignments.

Server-side decision sequence (verified in PermissionEvaluatorService)

  1. Action code must exist in ref.action_catalog; unknown codes are denied.
  2. A verified caller must exist; no principal means deny.
  3. Approval against the caller's own record is denied before role lookup.
  4. Only the selected active role assignment is considered. Multiple active assignments without a selected one can return 409 ACTIVE_ROLE_REQUIRED.
  5. The assignment scope must match the requested scope, subject to documented top-post coverage rules.
  6. The role definition must be ACTIVE and the role must hold the action in app.role_action.

Platform actions are evaluated separately by PlatformPermissionService. Platform users do not receive tenant roles. DPO approvals for tenant export, deletion and retention changes remain separate named actions.

16. Security, authorization, tenant isolation and audit

TenantContext

After JWT verification, request context carries tenant ID, isolation mode, institution scope (ALL, LIST or NONE), institution IDs, active role code, scope type, active assignment ID and active-role-required state. Context is cleared at request end.

PostgreSQL RLS

TenantRoutingDataSource applies tenant and institution GUCs to the connection before it is handed to Hibernate. A request with no tenant context leaves tenant scope unset; RLS should then expose no app.* rows. Institution IDs default to an empty set, not “all institutions”.

Platform separation

Platform principal is not a tenant principal. Platform staff do not receive blanket tenant data access. Support access is a deliberate exception that requires tenant grant and ticket-bound session controls.

Confidential workflows

ID cards, certificates, grievance submission/review and disciplinary routes set allowSupportSession=false or are identified as confidential. Support sessions cannot use those route bypasses.

V4.0 approval / roll-down safety rules

  • No self-approval; preparer is not approver.
  • Duplicate consecutive steps for the same person collapse to one recorded decision.
  • Own-leave approvers are not rolled down.
  • Students, parents, applicants, GBA and platform roles are not stand-ins.
  • Stand-in decisions display and log “Acting for …”.
  • Authority returns to the appointed role holder when the role is filled.
  • Locked actions include payroll totals / individual salary access and DPO-only export, deletion and retention approvals.

These are source-specified guardrails. The current branch contains server evaluator and role-assignment implementations; the latest CI failures mean the whole security acceptance set is not currently green.

17. UI state contract and design system

The frontend uses the Stillwater design tokens and shared components. The V4.0 UX specification says every screen should account for these seven states:

1 · Loading

Skeleton state; no fake data presented as live.

2 · Empty

Useful empty state with the next available action.

3 · Validation error

Summary plus field-level messages.

4 · Server error

Safe error and correlation ID; never stack traces.

5 · Permission denied

Explain lack of access; server remains authoritative.
