## Why this matters

The backend resolves the tenant from the request hostname, and the frontend now sends production API calls to the same origin. The repository has application and proxy configuration for wildcard routing, but production login will still fail until the real domain, DNS, TLS, Keycloak realms, and required secrets are provisioned and verified.

## P1. Wildcard DNS and HTTPS

Create a wildcard DNS record for the registered domain and point it at the production load balancer/host. The platform host must resolve to the same endpoint. Issue a wildcard certificate using DNS-01 validation; wildcard certificates cover one label only. Keep certificate material outside container images and rotate it before expiry.

The repository does not contain a real DNS provider, registered domain, load balancer, or certificate. See docker/production/README.md.

## P2. Same address for app and API

docker/production/docker-compose.yml runs the API privately and publishes only nginx on ports 80/443. The nginx template redirects wildcard HTTP tenant hosts to HTTPS, serves the frontend, proxies /api and /v1 while preserving Host and forwarded headers, rejects unknown/nested hostnames, and blocks Swagger/OpenAPI/H2 console paths.

Never publish API port 8080 to the public network.

## P3. Same-origin API calls

Production app/src/services/axios.ts uses the page origin plus /api. Local development continues to use port 8080 on the active tenant hostname. Do not set one fixed VITE_API_BASE_URL in production; each tenant must send API requests through its own hostname.

## P4. Tenant domain suffix

KeycloakProperties.tenantHostSuffix is configured through TENANT_HOST_SUFFIX, for example .example.edu. The production value has no default so an unset suffix fails startup. The resolver strips the longest configured suffix and accepts exactly one tenant label. Local development suffixes are also supported through the same property.

Use TENANT_HOST_SUFFIX=.example.edu and PLATFORM_HOST_LABEL=platform. The support-session hand-off uses SUPPORT_SESSION_TENANT_BASE_DOMAIN=example.edu (apex only, no leading dot), producing HTTPS tenant URLs in production.

## P5. CORS

Same-origin app/API calls do not need wildcard CORS. Production requires the exact platform origin in CORS_ALLOWED_ORIGIN; app.cors.allowed-origin-patterns remains blank. Do not use * or wildcard origin patterns.

## P6. Reserved subdomains

Tenant provisioning already rejects reserved labels, including platform, www, api, admin, auth, keycloak, mail, static, and status. Keep this set aligned with infrastructure-owned hostnames. Do not rename/remove a reserved label without a reviewed domain policy.

## P7. Keycloak frontend redirects

New tenant realms receive KEYCLOAK_FRONTEND_REDIRECT_URIS. Runtime provisioning also reconciles the frontend client in existing realms. Production values must be HTTPS patterns for the real wildcard domain, for example https://*.example.edu/*. Do not include localhost or HTTP development addresses.

Run the one-time realm migration in docs/KEYCLOAK_PRODUCTION_SETUP.md for all existing realms before enabling production login. KEYCLOAK_BASE_URL must produce the same issuer base as the tokens' iss claim.

## P8. Tenant address on screen

The tenant list derives the address from the active/configured domain rather than hard-coding .edu360.local. Recheck the displayed address on the real staging domain.

## P9. Custom domains (optional, separate decision)

Exact custom-domain lookup exists, but automated ownership proof and certificate provisioning are not part of the wildcard-domain release. Do not add arbitrary custom domains to the Keycloak redirect allowlist. Custom domains remain a separate higher-plan governance and infrastructure decision.

## P10. Token must match the address

TenantHostMatchingFilter resolves the request host and compares it with the authenticated tenant principal. A tenant token presented on another tenant hostname is rejected with HTTP 403 TENANT_HOST_MISMATCH. New unit and integration tests cover matching and mismatching hosts. Execute them in CI and include SEC-01 in the staging security test.

## P11. Realm-scoped Keycloak admin service accounts

Production uses client-credentials authentication rather than the master bootstrap password. The master-realm service account can create/delete realms and view/query realm metadata. Each tenant realm has a realm-local service-account user with manage-users, view-users, query-users, and view-realm. User operations obtain a token from the target realm; realm lifecycle operations use the master-realm client.

Run docker/keycloak/configure-production-clients.ps1 as documented in docs/KEYCLOAK_PRODUCTION_SETUP.md. Include every existing tenant realm in KEYCLOAK_TENANT_REALMS.

Credential caveat: the current configuration uses one shared client secret across realm-local client instances. Tokens are realm-scoped, but compromise of that shared secret can mint tokens in every configured realm. Treat it as a platform-wide privileged secret, restrict it to the API workload, and rotate it. Per-tenant secret distribution is a separate hardening item.

## P12. Identity-events service account

The bootstrap script provisions a separate edu360-identity-events client in edu360-platform and maps only the identity-events:write role to its service account. It uses a distinct secret and must not be reused for user administration. Set KEYCLOAK_IDENTITY_EVENTS_CLIENT_ID and KEYCLOAK_IDENTITY_EVENTS_CLIENT_SECRET in the deployment secret manager.

## Local development

- Tenant addresses use <subdomain>.edu360.localhost:5173; wildcard .localhost names resolve to loopback.
- The older .edu360.local style remains supported when the hosts-file helper is used.
- The dev profile uses HTTP and the Vite port for support-session hand-off. Production uses HTTPS and no frontend port.

## Keycloak authenticator extension

Production Keycloak must include the EDU 360 OTP extension for the in-app authenticator enrolment flow.

- Build the extension using its Maven project under docker/keycloak/edu360-otp-extension.
- Install the JAR into /opt/keycloak/providers/ in the production Keycloak image, then run kc.sh build before kc.sh start.
- The extension is built against Keycloak 26.0.8. Rebuild and re-test after every Keycloak upgrade.
- API calls to the extension use the realm-scoped admin client described in P11.
- Verify a two-step-role user with no authenticator sees the EDU 360 QR enrolment flow and can sign in after setup.
